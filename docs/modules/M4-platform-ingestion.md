# M4：平台数据接入与民宿自动归一化

## 状态

已验收，后续开发已进入 M8。

## 模块目标

建立可扩展的平台数据接入管道，将不同平台字段转换为统一的民宿、房型和价格结构，并通过可解释的组合评分识别跨平台同一家民宿。所有导入批次、原始数据、归一化结果和匹配决策均可审计。

本模块使用本地途家风格演示 JSON 验证完整流程，不抓取真实平台页面，也不绕过平台登录、验证码或反爬限制。

民宿新增统一走本模块的数据接入入口：开发阶段使用 JSON/CSV 演示文件，正式阶段优先使用平台开放接口、联盟接口、商家授权数据或正式合作数据。M4 负责导入、归一化、同店/房型匹配和审计，不负责管理员最终审核。

## 数据流程

```text
平台适配器
   ↓
原始平台 JSON
   ↓
字段归一化与价格校验
   ↓
同店候选评分
   ├── 自动匹配：写入已有统一民宿
   ├── 需要复核：保留候选但不自动合并
   └── 新民宿：生成稳定 public_id
   ↓
幂等更新平台房源、房型和价格快照
   ↓
记录导入批次、单条状态、分数与匹配证据
   ↓
提交待审核房源
   ↓
M13 管理员审核通过后进入可推荐数据
```

## 新增数据表

| 表名 | 用途 |
| --- | --- |
| `ingestion_batches` | 一次平台导入任务的来源、状态和统计结果 |
| `ingestion_records` | 单条平台原始 JSON、归一化 JSON、导入状态与错误 |
| `listing_match_records` | 候选统一民宿、匹配分数、决策和各项评分证据 |

原始业务数据仍写入 M1 的 `platform_listings`、`room_types`、`price_snapshots` 和设施关联表，因此 M2 查询 API 与 M3 前端页面不需要改变。

## 匹配策略

匹配总分范围为 0 至 1，由以下因素组成：

| 因素 | 权重 |
| --- | --- |
| 标准化名称相似度 | 45% |
| 地址相似度 | 30% |
| 经纬度距离 | 20% |
| 区域完全一致 | 5% |

- 分数不低于 `0.7800`：自动匹配。
- 分数在 `0.6200` 至 `0.7800` 之间：标记为需要人工复核，不自动建立新关联。
- 分数低于 `0.6200`：视为新民宿并生成稳定的 `SS_` 前缀公开编号。
- 匹配证据保存名称分数、地址分数、距离、坐标分数、区域结果和总分。

该规则属于可解释的确定性匹配，不是 AI 推荐模型。后续可以在保留审计结构的前提下替换或叠加向量相似度模型。

## 适配与归一化

`FixturePlatformAdapter` 负责将平台风格字段转换为内部结构，包括：

- `listingId` → 平台房源外部编号。
- `title`、`location` → 民宿名称和标准地址。
- 中文设施名称 → 标准设施代码。
- 平台房型 → 统一房型结构。
- 平台价格 → 房费、费用、优惠、总价和采集时间。
- 导入前校验入住日期、人数、非负金额和总价公式。

适配器遵循统一 `PlatformAdapter` 协议，后续可以增加官方 API、授权数据文件或其他合规数据源，而不修改匹配和写库逻辑。

### 支持的数据来源

| 来源 | 当前处理方式 | 正式使用要求 |
| --- | --- | --- |
| JSON/CSV 文件 | 通过适配器批量导入 | 文件字段符合模板，保留来源和更新时间 |
| 平台官方/联盟 API | 增加平台适配器同步 | 具备接口授权和调用限额 |
| 商家授权数据 | 按授权模板导入 | 保存商家授权范围和有效期 |
| 未授权网页抓取 | 不接入 | 不绕过登录、验证码或反爬限制 |

## 导入命令

安装 Make 后，在项目根目录执行：

```powershell
make data-import
```

当前 Windows 环境未安装 Make 时执行：

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File scripts\dev.ps1 data-import
```

也可以在后端目录直接执行：

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.modules.ingestion.cli `
  --platform tujia `
  --fixture fixtures\ingestion\tujia-demo.json
```

每次执行都会保留一个新的审计批次，但平台房源、房型和相同采集时间的价格使用业务唯一键幂等更新，不会重复增加。

## 只读审计 API

```http
GET /api/v1/ingestion/batches
GET /api/v1/ingestion/batches/{batch_id}
```

批次列表返回平台、来源、状态和成功/失败数量；详情接口返回每条平台记录对应的统一民宿、匹配分数、决策和评分证据。M4 不提供无鉴权的 HTTP 导入接口，避免开发环境中的写操作被误触发。

## 真实验证结果

途家演示数据包含 3 条平台房源、4 个房型及对应价格。重复执行三次后：

- 新增 3 个导入批次、9 条导入记录和 9 条匹配记录。
- 每个批次均接收 3 条、成功导入 3 条、失败 0 条。
- 9 条记录均自动匹配到已有统一民宿。
- 最新批次匹配分数分别为 `0.9357`、`0.8071`、`1.0000`。
- `canonical_listings` 保持 3 条。
- `platform_listings` 保持 7 条。
- `room_types` 保持 8 条。
- `price_snapshots` 保持 8 条。

## 自动测试

- 适配器平台身份校验。
- 平台字段、设施、房型和价格归一化。
- 同一家民宿的异名自动匹配。
- 明显无关房源不被错误合并。
- 三张审计表和匹配分数约束。
- 批次列表响应和批次不存在时的 404。
- M0 至 M3 原有测试回归。

## 不包含

- 未经授权抓取美团、途家、木鸟页面。
- 绕过验证码、登录限制或平台反爬机制。
- 管理员审核页面和手动合并操作（属于 M13）。
- 定时任务、消息队列和大规模并发采集。
- AI 推荐、用户画像和旅行规划。

## 验收步骤

1. 在项目根目录执行 `scripts\dev.ps1 data-import`。
2. 确认输出 `received_count: 3`、`imported_count: 3`、`failed_count: 0`。
3. 确认 `auto_matched_count: 3`，没有创建新的统一民宿。
4. 再执行一次相同命令，确认业务表数量没有增长。
5. 打开 `http://127.0.0.1:8000/docs`，找到 `ingestion` 分组。
6. 请求 `/api/v1/ingestion/batches`，确认可以看到导入历史。
7. 请求最新批次详情，确认三条记录都有统一民宿、分数和评分证据。
8. 打开前端首页，确认仍为 3 家民宿且价格未发生重复。
9. 执行 `scripts\dev.ps1 test`，确认全部检查通过。

## 通过条件

- 平台原始数据可以稳定转换为内部统一结构。
- 同店匹配结果可解释、可审计，并存在人工复核安全区间。
- 重复导入只增加审计历史，不重复增加业务房源、房型或价格。
- 导入错误可以定位到具体批次和记录。
- M2 查询与 M3 前端页面没有回归。
