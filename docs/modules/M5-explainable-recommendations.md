# M5：可解释的个性化推荐引擎

## 状态

待验收。

## 模块目标

根据用户的入住条件、预算、旅行风格、设施偏好和区域偏好，对当前可订民宿进行个性化排序，并返回总分、分项得分和自然语言推荐理由。推荐请求和结果会保存到 MySQL，便于复查算法版本和解释推荐结果。

M5 建立的是确定性、可解释、可测试的推荐基线，不调用外部大模型。后续 AI 模块可以基于这套可信候选和分项得分生成更自然的理由或进行受约束的二次排序，而不是让大模型直接编造价格和房源。

## 推荐流程

```text
用户偏好
  ↓
查询满足城市、日期和人数的可订民宿
  ↓
计算价格 / 评分 / 设施 / 平台覆盖 / 位置分数
  ↓
按照旅行风格应用不同权重
  ↓
稳定排序并生成 1 至 3 条推荐理由
  ↓
保存推荐会话、算法版本、分数和结果快照
```

## 请求参数

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `city` | 是 | 目的地城市 |
| `check_in` | 是 | 入住日期 |
| `check_out` | 是 | 离店日期，必须晚于入住日期 |
| `guests` | 否 | 入住人数，默认 2 |
| `budget_total` | 否 | 整个入住区间的预算总额 |
| `preferred_facilities` | 否 | 偏好设施代码，自动去重 |
| `preferred_districts` | 否 | 偏好区域，自动去重 |
| `travel_style` | 否 | `value`、`comfort`、`scenery` 或 `family` |
| `top_k` | 否 | 返回数量，默认 3，最大 10 |

## 评分维度

- 价格：最低候选获得最高价格分，超出预算时追加惩罚。
- 评分：平台最高评分除以 5，缺失评分使用保守中性分。
- 设施：显式偏好优先；没有显式偏好时使用旅行风格的默认设施集合。
- 平台覆盖：同一民宿可比较的平台越多，覆盖分越高，3 个平台封顶。
- 位置：位于偏好区域时满分，不在偏好区域时降低得分。

## 风格权重

| 风格 | 价格 | 评分 | 设施 | 平台覆盖 | 位置 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `value` 省钱型 | 50% | 20% | 15% | 10% | 5% |
| `comfort` 舒适型 | 20% | 30% | 30% | 10% | 10% |
| `scenery` 观景型 | 20% | 20% | 35% | 10% | 15% |
| `family` 家庭型 | 25% | 20% | 35% | 10% | 10% |

风格默认设施：

- 舒适型：无线网络、空调。
- 观景型：海景。
- 家庭型：厨房、洗衣机、一楼房型。
- 省钱型：不强加设施要求。

如果用户明确传入 `preferred_facilities`，显式偏好会覆盖风格默认设施。

## 新增数据表

| 表名 | 用途 |
| --- | --- |
| `recommendation_sessions` | 保存请求、风格、预算、算法版本和会话状态 |
| `recommendation_results` | 保存排序、民宿快照、总分、分项得分和理由 |

结果表保存民宿名称、公开编号、区域、总价和评分快照。即使房源之后更新，历史推荐仍然可以解释当时为何产生该结果。

## API

### 创建推荐

```http
POST /api/v1/recommendations
```

示例：

```json
{
  "city": "大理市",
  "check_in": "2026-10-02",
  "check_out": "2026-10-05",
  "guests": 2,
  "budget_total": 1600,
  "preferred_facilities": ["wifi", "kitchen"],
  "preferred_districts": ["大理镇"],
  "travel_style": "comfort",
  "top_k": 3
}
```

成功返回 HTTP 201、推荐会话编号、算法版本、会话状态和推荐结果。没有可订候选时仍保存请求，但状态为 `no_candidates`，结果数组为空。

### 读取历史推荐

```http
GET /api/v1/recommendations/{session_id}
```

返回创建推荐时保存的请求和结果快照；不存在的会话返回 HTTP 404。

## 推荐理由

理由来自真实分数和条件，不由模型自由生成，例如：

- 入住总价在你的预算内。
- 在当前可订候选中总价更有优势。
- 完整满足你关注的设施条件。
- 平台评分达到 4.8 分以上。
- 覆盖 3 个平台，价格可比性更充分。
- 位于你偏好的区域。

每个结果最多返回 3 条理由，避免重复堆砌。

## 真实验证结果

使用大理市、`2026-10-02` 至 `2026-10-05`、2 人和 1600 元预算：

- 省钱型首选 `DL_000002`，得分 `90.91`。
- 舒适型首选 `DL_000001`，得分 `94.08`。
- 观景型首选 `DL_000003`，得分 `81.30`。
- 家庭型首选 `DL_000001`，得分 `82.16`。
- 保存后的家庭型推荐会话可以重新读取，3 条结果、顺序、分数和请求保持一致。

## 自动测试

- 省钱型优先较低总价。
- 观景型提升海景民宿排名。
- 显式设施和区域偏好影响排序和理由。
- 日期校验与偏好去重。
- 推荐表和分数检查约束。
- 创建推荐返回 HTTP 201。
- 推荐会话不存在时返回 HTTP 404。
- M0 至 M4 原有测试回归。

## 不包含

- 用户注册、登录和长期用户画像。
- 前端推荐问卷和推荐结果页面。
- 调用 OpenAI 或其他外部大模型。
- 基于用户行为训练机器学习排序模型。
- 旅行计划生成、地图路线和景点安排。

## 验收步骤

1. 启动项目并打开 `http://127.0.0.1:8000/docs`。
2. 找到 `recommendations` 分组，调用 `POST /api/v1/recommendations`。
3. 使用大理演示日期分别提交 `value` 和 `scenery` 风格。
4. 确认省钱型首选 `DL_000002`，观景型首选 `DL_000003`。
5. 检查每条结果包含总分、5 个分项得分和不超过 3 条理由。
6. 复制返回的 `session_id`，调用历史推荐接口。
7. 确认读取结果与创建时完全一致。
8. 输入错误日期，确认接口返回 HTTP 422。
9. 输入没有演示报价的日期，确认状态为 `no_candidates`。
10. 执行 `scripts\dev.ps1 test`，确认全部自动化检查通过。

## 通过条件

- 不同旅行风格能够产生合理且稳定的不同排序。
- 推荐得分来自真实可订价格和房源信息。
- 每个推荐结果都可以解释，不返回无法追溯的结论。
- 推荐会话可以保存和重新读取。
- 无候选、输入错误和不存在会话均有明确状态。
- M2 查询、M3 前端和 M4 导入功能没有回归。
